# 架构与开发

本文描述当前代码结构。日常使用见[后台使用](后台使用.md)，协议细节见[接口与数据约定](接口与数据约定.md)。

## 站点边界

官网与后台属于同一 Nuxt 应用，共用服务端和数据库。后台为中文管理界面，官网支持已登记的五种语言。页面内容来自发布快照，UI 固定文案来自 `i18n/locales`；两者不能互相替代。

Studwell 与使用同一框架的其他站点采用源码实例化，各自拥有独立内容、品牌、数据库和部署。当前没有需要两站共同在线的中心服务，也没有已发布的框架依赖包。通用能力的修改应按实际需要在两站同步验证，不把某站的专属区块强行纳入通用核心。

| `app/api` | 前端请求路径、输入输出与传输 |
| `server/api`、`server/routes` | API 和公开文件路由 |

## 后台前端依赖

主要方向为页面／组件／布局 → composables → stores → API → 工具与共享合同，允许合理向下跨层。store 不反向导入项目 composables，API 不依赖 store，`app` 不导入服务端实现。

业务状态使用 Setup Store，按实际持有者拆分，不按文件数量或旧 composable 数量机械拆分。URL 是已生效查询条件的权威；输入中的搜索词和已提交条件分开保存。store 接收查询快照，不保存 route/router 对象。

身份变化、实体切换和离开页面后，旧响应不得覆盖新数据。写成功立即推进基线及版本，随后刷新失败必须保留“已保存”的事实。计时器、AbortController、File、密码和 DOM 不进入可序列化 SSR 状态；资源在离开、切换或销毁时清理。

后台通用组件位于 `app/components/admin/common`。API 不决定 Toast 或对话框；组件与公共反馈层负责展示，避免同一次会话恢复或写入重复通知。

## 服务端分层

入口装配 → Handler → Service → Repository → Drizzle／MySQL。

Handler 处理 HTTP、输入校验和响应；Service 负责授权、状态变迁、事务和审计；Repository 负责查询和持久化。同一业务事务内的调用必须使用同一个执行上下文，不在内部回退全局连接。

纯系统采集或无持久化需求的能力不必机械创建 Repository。不新增通用 CRUD 基类或低代码配置层来替代明确业务规则。可跨端共享的纯合同进入 `shared`，服务器授权和事务不进入前端共享层。

## 官网开发

`runtime` 提供可替换的默认外壳和基础运行机制，`sections` 表达站点内容。页头、页脚、首页遮罩可以作为运行模板保留、修改或删除；修改时保持导航、语言、SEO、页面加载及交互释放正确。

同组页面导航和本页侧栏是普通区块，按自身模板布局，不通过重排其他区块建立全页特例。新闻、招聘和咨询既有区块展示，也有专用业务接口，不能因为它们放在 sections 中就删除服务端业务能力。

官网代码不能依赖 `shared` 中后台专属合同。组件、动画、数据请求的改动需核对桌面与手机入口；SSR 与水合首帧保持一致。模板字段与新组件的完整流程见[页面与区块](页面与区块.md)。

## 修改和验证

既有迁移不改写，结构变更新增 SQL 并同步 Schema 与快照。权限判断、版本冲突、事务审计和文件生命周期不能只依赖 UI。新增字段同时检查编辑器、发布校验、预览、前台与搜索。

按改动运行相关测试、Lint、类型检查和构建；界面改动另检查实际交互。只改文档时核对链接、命令、路径和事实，不把历史测试计数写成重新执行的结果。

不在日志、示例或提交内容中包含真实密码、连接串、Cookie、Token 和私有部署值。维护人自行审阅、提交及发布；文档中的部署步骤不表示已在生产执行。
